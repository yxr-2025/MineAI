## 2. 紧迫度驱动的空闲（第 1 项）

固定 30 秒的问题在于它不随处境变化。按模型优先原则，空闲时长本身就是判断，应交给模型：

- 规划器新增 `rest(seconds, reason)`：模型明确说"现在没事做，N 秒后再看"。
- 代码只做边界约束：`seconds` 夹在 5–600 之间，缺省 30 秒。
- 状态栏显示倒计时（`rest=27s → 19s → 11s`）。

安全反射（属于安全边界，允许保留在代码里）：满足任一条件时立即唤醒，不睡：

- 生命 < 30%
- 氧气 < 60
- 8 格内存在敌对生物

实机证据：`agent=IDLE mode=life rest=27s`，随后 `THINKING` 重新评估。

## 3. 累积式反思（第 2 项）

原来每个目标结束都反思一次，调用过密。现在改为计数触发：

```text
目标结束
  ├─ 失败：failureStreak++，successStreak=0
  │        失败次数 >= reflection_min_failures -> 反思
  └─ 成功：successStreak++，failureStreak=0
           成功次数 >= reflection_success_interval -> 反思
不触发反思时直接推进（下一步 / 重规划）
```

配置项：`reflection_min_failures`（默认 1，失败优先学习）、`reflection_success_interval`（默认 3）。

失败判定：本目标内是否出现工具失败、动作失败、超时或达到步数上限。

实机证据（真实教训被写入并持久化）：

```text
lessons=3
- 反复调用 collect_state 而不行动，卡住了；每次状态检查都要配一个具体动作
- 赤手打僵尸代价极高（掉到 7.5 血）；必须先采集木材、用箱中 32 铁锭造铁剑再交战
- 威胁已清除，但战斗方式需要改进
```

## 4. 依赖图计划（第 3 项）

`plan` 从字符串列表升级为 `Plan`（步骤图）：

- 步骤含 `id`、`goal`、`depends_on`、`status`。
- `next()` 只返回依赖全部 DONE 的 PENDING 步骤。
- `markFailed(id)` 会把所有传递依赖标记为 SKIPPED，使计划不再空转。
- 规划器提交计划时检测环（`Plan.hasCycle`），有环则要求重写。
- 计划摘要连同状态注入提示词，模型能看到进度与阻塞。

实机证据（模型自建 5 步依赖链）：

```text
[PENDING] craft_sword: 用箱中 32 铁锭在工作台打造铁剑
[PENDING] gather_wood: 去橡树采集木材 (after craft_sword)
[PENDING] clear_hostiles: 用铁剑清除敌对生物 (after gather_wood)
[PENDING] get_food: 获取食物 (after clear_hostiles)
[PENDING] eat_food: 进食恢复生命 (after get_food)
```

失败后自适应：新一轮计划以 `escape_zombies` 开头（因为生命危急）。

## 5. 通用结构识别（第 4 项）

原来只识别固定方块类。现在分两层：

**分类**（`StructureScanner.classify`）：

- 方块实体：任何 `BlockEntity` 是 `Container` → `container`；其它 `hasBlockEntity()` / `EntityBlock` → `block_entity`（覆盖模组方块）。
- 标签：`LOGS` / `LEAVES` / `CROPS` / `FLOWERS` / `SAPLINGS` / `DOORS` / `BEDS` / `CLIMBABLE`，以及 Forge 的 `Tags.Blocks.ORES`。
- 具体类型：工作台、熔炉类、床、门、耕地、刷怪笼、水、岩浆、铁砧、钟。

**聚类**：可成结构的类别（log / leaves / ore / water / crop / flower）用六向洪泛合并，输出一条 `structure: true` 条目，含方块数、中心、包围盒尺寸，而不是几十条单方块记录。

实机证据（模型读到的是结构而非散点）：

```text
- Chest (2,-60,0) 含 32 铁锭
- Crafting table (3,-60,0)
- Oak tree at (5,-59,5)：4 格树干 + 树冠
- Pond at (10,-61,10)：3x3 水源
```

## 6. 跨 NPC 协作（第 5 项）

`SharedBlackboard` 是所有 NPC 共享的事实板，持久化到 `config/mineai/blackboard.json`（上限 50 条）。

- `share(key, value)`：发布事实，记录作者。
- `read_board()`：读取全部事实。
- 黑板内容注入系统提示词与规划提示词，因此每个 NPC 天然看到同伴的发现。
- `/npc board` 供人工查看。

实机证据：

```text
npc_1 -> share base_camp = "At (0,-60,0): chest (2,-60,0) with 32 iron ingots, crafting table ..."
npc_2 -> read_board，前往该地点，并逐项核实箱子/工作台/橡树/水池均与 npc_1 描述一致
```

## 9. 已知限制

- 安全反射的阈值（30% 生命 / 60 氧气 / 8 格敌人）是硬编码常量，未做成配置。
- 反思阈值是全局的，不区分目标类型；同一目标反复失败只累积计数，不专门针对该目标。
- 计划依赖是"全部前置完成"语义，没有条件分支、循环或可选步骤。
- 结构聚类上限 256 方块/簇、48 条特征，超大结构会被截断。
- 黑板是最后写入优先，没有冲突消解或过期淘汰（只按容量淘汰）。
- 协作是"读事实"级别，没有任务分配或角色协商。

## 10. 后续可选方向

1. 安全阈值配置化，并按危险类型区分唤醒策略。
2. 反思阈值按目标指纹分组，专门针对重复失败。
3. 计划支持条件步骤与可选分支。
4. 黑板带 TTL 与置信度，避免过期信息误导。
5. 协作升级为任务认领（谁去做、做到哪一步）。
