# MineAI 阶段 8：客观验收、循环守卫、配方查询与步数预算

> 状态：已实现并在开发服务器上用真实 LLM 验证（机制生效；长链任务仍未由 agent 独立完成）
> 前置：阶段 0-1 ~ 7
> 目标版本：Minecraft 1.20.1 / Forge 1.20.1-47.2.0 / Java 17
>
> 后续阶段见 `docs/阶段9_任务靶场与阶梯度量.md`（任务靶场、任务阶梯、工坊世界与第一份度量）。

## 1. 背景

阶段 7 的"徒手从零造冶金灌注机"失败，复盘出的根因不是模型笨，而是**代码把"是否完成"和"该做什么"都交给了模型自己判断**：

- 模型拿到木镐就宣布完成，控制器照单全收；
- 反复 `collect_state` / `goto` 空转，没有循环检测；
- 步数预算按"目标"给，耗尽即整轮结束；
- 模型不知道配方，只能靠记忆猜；
- 掉落物拾取失效（阶段 7 已修）。

本阶段按 P0 → P1 → P2 顺序逐条修掉。

## 2. P0-1 客观验收（Objective）

新增 `agent/Objective`：**代码可判定的成功谓词**。

```java
record Objective(Type type, String itemId, int count)   // 目前支持 HAVE_ITEM
```

- 命令入口：`/npc agent obtain <item> <count> <goal>` 由操作者直接声明。
- 模型也可用 `declare_objective(item, count)` 自行声明。
- 计划步骤可携带 objective（`set_plan` 的每个 step 支持 `objective` 字段）。

控制器在目标结束时**先验收再接受**：

```text
模型无 tool_calls（声称完成）或步数耗尽
  -> objectiveMet() ? 接受 : 拒绝
  -> 拒绝时：注入"未达成（当前 0/1）"，重置步数预算，重新决策
  -> 最多 4 次，仍不满足才判失败
```

**关键点：模型负责干活，代码负责判卷。** 这是本阶段最重要的一条。

实机证据：

```text
[mineai] agent npc_1 finish rejected, objective unmet (0/1), nudge 1
[mineai] agent npc_1 finish rejected, objective unmet (0/1), nudge 2
[mineai] agent npc_1 finish rejected, objective unmet (0/1), nudge 3
[mineai] agent npc_1 finish rejected, objective unmet (0/1), nudge 4
```

模型连续 4 次试图提前收尾，全部被代码挡回。

## 3. P0-2 循环守卫

`noteCall` 记录最近 16 次 `(tool, args)` 的连续重复次数：

- 同一调用连续 3 次 → 不执行，注入"你在原地打转，换个方法"，重新决策。
- 累计 2 次警告 → 自主模式强制重规划；单目标模式判失败。

## 4. P0-3 空响应协议纠正

实测发现模型被拒后会返回**既无文本也无工具调用的空响应**，导致立刻再次收尾。新增：

```text
空响应（content 为空且无 tool_calls）
  -> 注入"必须且只能回复一个工具调用"，重新决策（最多 2 次）
  -> 之后才允许按正常收尾流程处理（仍受 objective 拦截）
```

## 5. P1-1 配方查询

新增 `agent/RecipeLookup` 与 `recipe_for(item)` 工具：

- 合成：产物与产量、按物品聚合的原料数量、**是否需要工作台**。
- 熔炼：输入物、是否需要燃料。

目标物品的配方会**自动注入**系统提示词与规划提示词，规划器不必再猜。

实机证据：模型主动调用 `recipe_for` 查询 `mekanism:ingot_osmium` 的制法。

## 6. P1-2 每步独立预算

`startPlanStep` 现在会把 `step` 重置为 0，并加载该步自己的 objective：

- 单步预算 = `max_steps`，12 步计划即有 12 份预算，不再一个大目标耗尽即整轮结束。
- 单步失败只影响该步（依赖它的步骤标记为 SKIPPED），不会拖垮整轮。

## 7. P2 其他修复

- **拾取半径**：从 1.0/0.5 放宽到 1.5/0.75，容错更好。
- **攻击充能异常**：`attack_charge` 恒为 0.2（`attack_cooldown_ticks` 为 5.0），说明 `attackStrengthTicker` 未累积。已确认 `Player.tick()` 确实在运行（`playerTicks` 同步增长），但成因未定，暂未修，不影响本任务的挖矿/合成路径。
- **饥饿不自然下降**：同属待查项，本任务不受影响。

## 8. 实机结果（诚实记录）

机制全部生效：

| 机制 | 证据 |
| --- | --- |
| 客观验收 | 连续 4 次拒绝未达成的收尾 |
| 步数预算重置 | 状态从 `step=59` 回到 `step=3` |
| 空响应纠正 | 多次 `empty response, re-prompting` |
| 配方查询 | `tool recipe_for -> recipe for mekanism:ingot_osmium` |

**但长链仍未走完**：agent 在"向下挖石头"阶段挖了一个 1×1 竖井，掉落物掉在井底，`goto` 进不去，随后反复尝试并多次返回空响应，最终 4 次验收拒绝后判失败。

## 9. 第二批：四条改进（已实现）

### 9.1 显式缺口清单（GapAnalyzer / missing_for）

`agent/GapAnalyzer` 从目标物品出发，**递归展开配方树并逐层扣减背包**，输出扁平清单：

```json
{"item":"minecraft:raw_iron","need":4,"have":0,"missing":4,"source":"gather"}
{"item":"minecraft:furnace","need":2,"have":0,"missing":2,"source":"craft"}
{"item":"mekanism:ingot_osmium","need":1,"have":0,"missing":1,"source":"smelt"}
```

已满足的分支会被剪掉。通过 `missing_for(item, count)` 工具按需查询，模型不必再自己记账。

### 9.2 挖竖井自陷守卫

`MineTool` 拒绝挖掘**正脚下**的方块，并返回明确原因：

> that block is directly under your feet; mining it would trap you in a one-wide shaft.
> Mine the block beside you and step down instead.

因为相邻挖一格再下去只形成 1 格落差（可跳回），这自然把行为引导成阶梯式挖掘。

### 9.3 目标模式（plan）跑长链

`/npc agent obtain <item> <count> <goal>` 现在走 **plan 模式**：

- 规划器产出依赖计划，每步有独立步数预算；
- 每步结束时用 `missionObjective`（或该步自己的 objective）验收；
- 计划跑完仍未达成 → 拒绝收尾并强制重规划（上限 4 次）。

### 9.4 分层模型（可配置）

`LlmConfig` 新增 `planner_model`；`LlmService.planner()` 供规划与反思使用，未配置时回落到执行模型。

实测发现**该中转站的 pro 类模型普遍不支持 function calling**：

| 模型 | set_plan 工具调用 |
| --- | --- |
| deepseek-v4-flash | ✅ |
| kimi-k2.7-code | ✅ |
| minimax-m3 | ✅ |
| mimo-v2.5-pro | ✅ |
| deepseek-v4-pro | ❌ 空响应 |
| deepseek-v4.1-flash / glm-5.3 / qwen3.8-max | ❌ |

所以分层能力已就绪，但当前默认 `planner_model` 留空（单模型）。选 planner 前必须先验证其工具调用。

### 9.5 精简后的规划提示词

把大段缺口 JSON 和嵌套 objective schema 塞进规划提示词后，**连 flash 都开始返回空响应**。改为：

- 缺口清单只保留工具入口（`missing_for`），不注入提示词；
- `set_plan` 的每步只保留 `id` / `goal` / `depends_on`，去掉嵌套 objective；
- 步骤的验收回落到 `missionObjective`。

精简后规划恢复正常（`tools=[set_plan]`，8 步计划）。

## 10. 当前瓶颈与诚实结论

代码侧的兜底已经相当完整：客观验收、循环守卫、空响应纠正、配方查询、缺口清单、自陷守卫、每步预算、分层接口。

agent 在本轮从零走到：**原木 9 + 木剑 + 木斧 + 木镐 + 木棍**，计划推进到第 2 步（tools）。但仍未走完长链，剩余失败点是**模型的长程执行质量**：

- 反复在同一个局部（雪地树丛/竖井）打转，不推进计划；
- 会用 `screenshot` / `scan_area` 反复侦察而不动手；
- 被拒绝后倾向重复同一动作或返回空响应。

这些已不是代码缺口。下一步只能从模型侧解决：

1. **选一个真正会规划的模型**（需先验证工具调用），或自建小模型微调；
2. 把计划步骤再切细（每步 3-5 个动作），降低单步的决策复杂度；
3. 用 `noul` 式校准判定"这一步到底做没做"，而不是依赖模型自述。

## 12. 已知限制

- `Objective` 目前只支持 `HAVE_ITEM`；`BLOCK_AT` / `ENTITY_DEAD` 等未实现。
- 客观验收只拦截"收尾"，不校验中间步骤的正确性。
- 循环守卫按"连续完全相同调用"判定，对"交替两种动作"的循环无效。
- 攻击充能仍异常（`attack_charge` 恒为 0.2）。已把 `AttackAction` 改为**多 tick 持续攻击**绕开它，但根因未定位。
- 饥饿 tick 仍未定位。
- `GapAnalyzer` 只走合成/熔炼，不覆盖需要机器加工（如 Mekanism 灌注）的中间产物。
- 分层模型依赖上游是否支持 function calling，pro 类模型在本中转站不可用。
- 长链任务仍依赖模型自身的规划质量。
