# 设计原则：模型优先，不手造轮子

> 状态：项目长期约束
> 适用：MineAI 全部后续开发

## 1. 原则

**凡是"选择、判断、规划、总结、复用"这类决策，交给模型；代码只提供信息与原子能力。**

代码不再编码决策策略。判断标准：

- 如果一段代码在做 `if/else` 式的"选哪个"，它大概率该被删掉，换成给模型看的信息 + 一个动作。
- 如果一段代码在做确定性算法、物理、协议、持久化、安全边界，它必须保留。

## 2. 边界：什么不能交给模型

| 类别 | 例子 | 原因 |
| --- | --- | --- |
| 确定性算法 | A* 寻路、碰撞、破坏进度、门/梯判定 | 搜索与几何问题，模型既慢又不可靠 |
| 物理与机制 | 游泳速度、氧气结算、攻击冷却公式 | 是引擎规则，决策改不了 |
| 协议与持久化 | 假连接、玩家列表、记忆落盘、配方解析 | 正确性要求确定 |
| 安全边界 | 工具白名单、坐标/距离校验、限流 | 不能由被约束方自己决定 |
| 每 tick 路径 | 移动步进、重力、朝向 | 延迟与成本不可接受 |
| 传输可靠性 | HTTP 重试退避、超时 | 基础设施，不是判断 |

## 3. 代价（必须承认）

把决策交给模型不是免费的：

- **延迟**：一次判断 = 一次 LLM 往返（1–3 秒）。所以只适合"低频决策"，不能进每 tick 循环。
- **成本**：token 消耗随对话增长。
- **可靠性**：模型可能给出无效答案，必须有工具层校验兜底。

因此规则是：**低频 + 需要判断 + 有原子能力可用** 三者同时满足，才交给模型。

## 4. 对现有代码的处置清单（已执行）

> 2026-09-19 完成第一批替换：源码 78 → 74 个文件，工具 19 → 17 个。
> 实测确认：模型自主 `equip` 工具、自主 `query_block` 验证、自主 `save_skill`；`equip` + `use` 可完成进食（食物 6 → 20）。

### 删除（手造的决策轮子）

| 现状 | 替代方式 |
| --- | --- |
| `action/ToolSelector`（按 `getDestroySpeed` 自动选镐） | 新增 `equip` 工具，模型自己选 |
| `EatAction` 内"营养最高的食物"选择 | 模型用 `equip` + `use` 自己选 |
| `AgentController` 的 `pendingVerification` 验证 nudge | 写进系统提示词，模型自觉验证 |
| `AgentController.autoSaveSkill`（自动抽技能） | 模型显式调用 `save_skill` |
| `agent/SkillRunner` + `run_skill`（手写重放器） | 模型用 `recall_skill` 读取步骤后自行重发 |
| 系统提示词内置地形摘要 | 模型按需调用 `scan_area` |
| `tool/FleeTool`（手算逃离向量） | 模型从 `collect_state` 拿到威胁坐标后用 `goto` |
| `tool/EatTool`（自动挑食物） | 模型 `equip` + `use` |

删除的文件：`ToolSelector`、`EatAction`、`EatTool`、`FleeTool`、`SkillRunner`、`RunSkillTool`。
新增的原子能力：`EquipTool`、`RetryingProvider`（`UseAction` 改为多 tick，接管使用时长这一机制）。

### 保留（不是轮子）

`AStarPathPlanner`、`NpcLocomotion`、`NpcTraversal`、`ProgressiveMineAction`、`NpcConnectionFactory`、`AgentMemory` 持久化、`ToolRegistry` 白名单、`RateLimitedProvider`、`LlmConfig`、`WorldStateCollector`。

### 补齐（给模型"眼睛"和"手"）

| 缺口 | 动作 |
| --- | --- |
| 氧气不可见 | `collect_state` 增加 `air` |
| 攻击冷却不可见 | `collect_state` 增加 `attack_cooldown` |
| 不能换装备 | 新增 `equip(slot 或 item)` 工具 |
| 超时即整轮失败 | provider 层重试退避；失败作为观察回传，模型自行重规划 |

## 5. 提交前自检

新增代码前问一句：

1. 这段逻辑是在"做判断"还是在"提供能力"？
2. 如果是判断，模型能不能在拿到信息后自己做？
3. 交给模型的频率是低频吗？延迟可接受吗？
4. 有没有工具层校验兜底？

四个问题里只要有一个答案指向"不该交"，就保留代码实现。
