# MineAI 阶段 10：可执行技能（把 LLM 移出内循环）

> 状态：已实现并验证（技能确定性重放，2 步动作只花 1 次 LLM 调用）
> 前置：阶段 0-1 ~ 9
> 目标版本：Minecraft 1.20.1 / Forge 1.20.1-47.2.0 / Java 17

## 1. 为什么做这个

阶段 9 的度量指出真正的瓶颈：**每个动作都要一次 LLM 往返**（约 10–20 秒/步）。100 秒只买得起 5–10 步，而多数阶梯任务需要 10–20 步。所以任务不是"模型不会"，而是"太贵太慢"。

解法是把**已知流程**做成可执行程序：验证一次，之后确定性重放，LLM 只在失败时介入。

## 2. 技能格式的变化

阶段 3 的技能只是"工具调用轨迹"，`recall_skill` 还要模型逐步重发。现在：

```java
record Skill(String name, String description, List<JsonObject> steps, int uses,
             int originX, int originY, int originZ)
```

三处关键变化：

1. **只保留可执行原语**：`goto / mine / place / use / equip / craft / insert_item / extract_item`。
   侦察类（`collect_state` / `scan_area` / `query_block` / `screenshot`）与记忆类步骤在保存时被过滤掉，重放不再浪费调用。
2. **记录原点**：保存时记录 NPC 当时的坐标。
3. **锚点平移**：执行时给一个 anchor，所有坐标按 `anchor - origin` 平移，同一技能可在不同地点复用。

## 3. 执行器

`SkillRun` 保存一次执行的进度（技能、锚点、当前步骤、是否在等动作、已用 tick）。

`AgentController` 新增 `RUNNING_SKILL` 状态，每服务器 tick 推进：

```text
RUNNING_SKILL
  ├─ 动作队列忙 -> 等待
  ├─ 上一步是排队动作 -> 读 lastResult，失败则中止
  ├─ 取下一条步骤 -> 平移坐标 -> 调用对应工具
  │    ├─ 工具失败 -> abortSkill（把失败原因作为观察交回模型）
  │    └─ 工具排队 -> 标记等待
  └─ 全部走完 -> finishSkill（记 uses、把成功作为观察交回）
```

**步骤之间没有任何模型调用。** 失败时中止并附上具体原因（第几步、哪个工具、什么原因），模型据此修复或重录技能。

## 4. 入口与提示词

- `run_skill(name, x, y, z)`：x/y/z 为可选锚点，缺省用当前位置。
- `save_skill` 现在保存**过滤后的可执行技能**并记录原点。
- 系统提示词明确：`run_skill` 会重放整套流程而不再逐步决策，**优先用 `run_skill` 而不是一步步做**。

## 5. 验证

预置一个技能（2 步：走到锚点旁、挖掉锚点下方方块），让模型调用 `run_skill`：

```text
[mineai] agent npc_1 running skill 'digbeside' (2 steps) at BlockPos{x=10, y=-60, z=3}
[mineai] agent npc_1 tool run_skill -> running skill 'digbeside' (2 steps, no further decisions needed)
[mineai] agent npc_1 skill 'digbeside' completed
```

核验：`(10,-61,3)` 变为空气（`Test passed`）。

**2 步动作 = 1 次 LLM 调用**（就是那次 `run_skill`）。

失败路径同样验证过：另一个技能把"走到方块上再挖它"录了进去，执行器在第 2 步被自陷守卫拦下，并回报：

```text
skill 'digstone' aborted: step 2 (mine) failed: that block is directly under your feet; ...
```

——确定性执行 + 精确失败交回，正是设计目标。

## 6. 效果与成本

| | 逐步决策 | 可执行技能 |
| --- | --- | --- |
| 2 步动作的 LLM 调用 | 2+ 次 | 1 次 |
| 15 步流程 | 15+ 次（约 3 分钟） | 1 次 + 确定性执行 |
| 失败处理 | 每步都可能跑偏 | 中止并带原因交回 |

技能越长，收益越大；而技能的正确性由"录制时成功过一次"保证。

## 7. 已知限制

- **录制质量决定一切**：录制时若把侦察/验证步骤混进去（已过滤）或录了会自陷的动作（如"走到方块上再挖它"），重放就会失败。目前靠执行器中止 + 模型修复，没有录制期校验。
- 技能没有**前置条件校验**（比如"需要木镐"），失败只能在执行中暴露。
- 坐标平移是整体位移，不处理"目标结构在不同地形需要不同走位"。
- 没有**技能组合**（技能调技能）。
- 技能库靠模型显式 `save_skill` 积累，冷启动慢。
- 技能失败后模型若仍不修复，会回到逐步模式。

## 8. 下一步

1. **录制期校验**：保存技能时用 `mine` 的自陷守卫等规则做一次静态检查，拒绝明显会失败的程序。
2. **前置条件**：技能声明所需工具/材料，执行前校验并给出明确缺口。
3. **技能组合**：允许技能引用技能，把 `craft_wooden_pickaxe` 组装成 `craft_stone_pickaxe`。
4. **冷启动**：让规划器在第一次解决某类任务后自动建议 `save_skill`（现在已在提示词里，但模型经常忘）。
5. 回到阶段 9 的阶梯，测量"第二次运行同一任务"的耗时下降。
